# DiOS 交付评审：责任与决议

评审人根据固定版本、验收要求和工程证据，判断是否可以接受交付，以及哪些问题必须在发布前解决。开发方负责实现、构建、部署、自动化测试、证据定位和问题修复。

## 每次评审需要完成的事

1. 阅读对应工作项的验收条款、适用范围和已知缺口，确认交付范围符合四层架构。
2. 抽查关键证据与实现是否一致。对权限绕过、重复执行、恢复后双写、未知结果重放等高影响事项，检查失败路径和恢复条件；有疑点时要求开发方演示或补证据。
3. 给出“通过”“有条件通过”或“需修订”，绑定提交 SHA；有条件通过须写明接受的残余风险、责任人、关闭条件和复审触发条件。

工程证据不足的条款保留未完成状态。用户产品验收、工程测试和技术评审分别记录，不相互替代。

## 角色与具体判断

| 角色 | 判断内容 | 输出 |
| --- | --- | --- |
| 架构/模块责任人 | DiOS 是否保持能力域边界；协议、兼容和生命周期是否自洽 | 接受范围、接口或实现修订项 |
| 安全评审人 | 身份与委派是否收窄；E2AG 是否在实际动作处生效；撤权、审批与失败是否存在绕过 | 威胁与残余风险结论、发布前必修项 |
| 测试/运维与发布责任人 | 安装、升级、回退、恢复与诊断是否可操作；证据是否覆盖声明的部署条件 | 可交付条件、运行限制、发布接受结论 |
| 产品责任人 | 范围与产品使用是否满足目标；上层客户业务由独立应用验收 | 产品验收结论与后续优先级 |

人员可兼任角色。按照[工程手册](handbook.md)，高影响权限、迁移、副作用和生产变更需要实现者之外的合适评审人；AI 提供分析与证据，指定责任人给出接受结论。
