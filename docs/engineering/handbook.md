# DiOS 工程手册

版本：0.3 · 状态：已接受（G0）。适用于架构、接口、实现、扩展和企业交付。

## 1. 文档体系与权威来源

| 材料 | 解决的问题 | 位置与维护责任 |
| --- | --- | --- |
| 产品目标与范围 | 服务谁、交付什么、阶段优先级 | ROADMAP；产品责任人 |
| 架构基线 | 原则、边界、协作与部署逻辑 | docs/architecture；架构责任人 |
| ADR | 重要选择为何成立、替代方案及后果 | docs/adr；决策提出人与相关域评审人 |
| 领域/API/权限设计 | 对象、Schema、状态机、失败与兼容语义 | docs/design；模块责任人，机器可读契约随模块维护 |
| 运维与交付文档 | 安装、升级、备份、恢复、告警、应急 | docs/operations；交付与运维责任人 |
| 验收证据 | 哪个版本在何种条件下满足要求 | 对应 PR/发布及版本化报告；测试与模块责任人 |
| 执行任务与依赖 | 谁交付、何时开始、如何验收 | GitHub Issue / Project；任务负责人 |

设计文档采用 [设计模板](../templates/design-spec.md)，重要决策采用 [ADR 模板](../templates/adr.md)，评审采用 [评审模板](../templates/review.md)。文档中的图、术语和接口与对应版本同步；演示、导出 HTML 和客户材料引用源文档。

每份正式设计包含：文档标识、状态、责任人、关联需求/Issue、适用代码版本、依赖决策和最后评审日期。状态依次为草案、待评审、已接受、已替代/废弃。接受记录引用提交 SHA；已接受 ADR 保留历史，变更通过新的 ADR 取代。

## 2. 责任与评审

产品责任人确认场景、范围和业务验收；架构责任人确认跨层边界与关键取舍；模块责任人负责设计实现、迁移和接口兼容；安全评审人负责身份、授权、数据与供应链；测试/运维责任人确认可验证性、故障恢复与交付。

人员可以兼任角色。权限边界、数据迁移、外部副作用和生产部署等高影响变更需要另一位合适的评审人；暂无人选时记录待认领及评审阻断。AI 可以起草、实现和提供证据，接受决策由指定责任人确认。

## 3. 从架构到发布的门槛

| 门槛 | 输入 | 通过条件 | 解锁事项 |
| --- | --- | --- | --- |
| G0 架构基线 | 原则、图解、需求追踪、工程规则 | 责任边界清楚；原则冲突和授权绕过问题关闭；待决项有承接；评审有决议 | F01-1 领域/API、F01-2 容量设计 |
| G1 详细设计 | Schema、状态机、授权矩阵、失败语义、ADR | 必要选型达成；兼容、迁移、验收和责任人明确 | 对应实现任务 |
| G2 可合并实现 | 代码、契约、文档、测试、迁移方案 | 代表性端到端及相关安全/恢复测试通过；消费者同步；评审通过 | 合并并进入发布候选 |
| G3 可交付版本 | 固定版本、部署说明、备份/回退、运行证据 | 环境和依赖清单明确；安装升级恢复通过；发布责任人接受残余问题 | 试点或生产发布 |

G0 后可以并行开展彼此独立的详细设计。G1 按任务与依赖生效；跨层契约的消费方参与评审。轻量修正使用简短变更说明，结构、权限、持久状态和外部行为变化提交完整设计与相关 ADR。

## 4. Issue 与 Project 管理

一个可执行任务描述一个可验收结果，包含需求/原则编号、范围、交付物、依赖、验收、责任人和证据。工作包归集子任务；原生 Parent/Sub-issue 表达层级，Blocked by 表达开工前置。

Stage 表示 P0—P4 阶段；Layer 表示责任层；Priority 表示优先级；Wave 表示批次；Readiness 表示依赖是否满足；Status 表示实际执行进度。

- **Todo**：尚未启动。前置任务验收后，Readiness 设为可开始。
- **In Progress**：已启动，包含待评审和验收修订；Issue 明确当前阻断与下一次交付。
- **Done**：交付物与验收证据已关联，Issue 已按完成关闭。关闭为不实施的任务单独写明决议，检查依赖替代关系。

任务认领时设置 Assignee 与合理交付时间。依赖完成后重新判断下游就绪状态；出现新阻断同步原生依赖。Project 状态反映真实进展，同步脚本不得把已启动或已完成任务重置为 Todo。

每个工作周期检视可开始队列、阻断、在制任务和依赖变化；每个里程碑复核验收证据、风险与容量。新增场景关联通用能力或应用任务，并记录对范围和阶段的影响。

## 5. 变更、兼容与测试

Issue → 设计/ADR → PR → 验收证据 → 发布形成追踪链。PR 说明问题、最终行为、影响契约、迁移/恢复方式及验证结果，关联需求与任务。涉及公共行为时，检查 API、CLI、Console/门户和扩展消费者。

每个 API/事件契约定义版本、身份与权限、Schema、错误分类、幂等键、分页、关联标识和兼容策略；事件另定义顺序、重放、去重与保留。废弃接口需要迁移路径和兼容期限。凭据只使用 Secret 引用，不进入示例、截图或日志。

测试按变更风险选择：领域不变量用单元测试，服务边界用契约测试，数据库/队列用集成测试，关键工作闭环用端到端测试，授权与审批用攻击/负面用例，运行可靠性用故障注入与恢复演练。界面行为变更补充实际浏览器验收。文档修订检查链接、术语、图文一致与导出效果。

数据库变更采用向前兼容扩展、迁移、消费方切换和清理的节奏。每次迁移记录适用版本、备份点、恢复方式和不可逆项。应用回滚、数据恢复与外部业务补偿分别定义。

## 6. 发布与企业交付

发布清单包含代码提交与构建摘要、依赖和扩展版本、配置 Schema、数据库迁移、部署拓扑、所需权限/网络、备份/恢复步骤、已知问题与验收报告。部署规模与可用性声明引用实测负载和故障条件。

运维文档说明健康检查、队列积压、授权失败、工具错误、成本异常和存储容量的告警及处置。生产变更保留责任人与审计记录，升级前验证兼容窗口及恢复路径。

依赖与扩展登记来源、许可证、版本和更新责任；插件包分发、后端产品部署、商业授权分别评估。模型和外部服务限制进入容量与成本假设。

## 7. 风险、例外与决策记录

风险记录包含影响、触发条件、责任人、缓解措施和复核日期。阻断架构或发布的风险进入 Issue 原生依赖。原则例外通过 ADR 记录范围、理由、补偿措施、有效期和退出条件；到期重新评估。

基线变更复核受影响的原则、图、详细设计、任务、测试和交付说明。当前基线评审使用 [v0.3 评审记录](../architecture/review-v0.3.md)；详细设计入口为 [领域与容量交付记录](../design/review-f25-f26.md)。
