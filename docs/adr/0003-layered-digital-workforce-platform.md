# ADR 0003：DiOS 内核、数字员工服务与业务应用三层架构

- 状态：已接受
- 日期：2026-11-11
- 相关：[Roadmap](../../ROADMAP.md)、[架构说明](../architecture.md)、ADR 0001、ADR 0002
- 实现状态：本 ADR 确认目标边界；领域 API、数据模型与验收按 Roadmap P0—P4 交付。

## 背景

现有 DiOS 具备事件、资源注册、Agent 运行和治理基础。企业数字员工进一步需要组织岗位、持久身份、工作空间、任务协作、知识、开发发布和运营。三类应用均可复用这些企业服务，同时保留各自的业务流程。

单机作为初期开发验证基线；可扩展企业部署是产品目标，单企业多用户是首期访问模型。参考场景用于检验通用能力，行业范围保持开放。部署规模与租户模型分别设计。

## 决策

### 1. 建立三层产品结构

- L1 DiOS 内核：资源、Agent 生命周期、事件、调度、运行时、身份校验、授权执行、Secret、Approval Gate、配额、证据和恢复。
- L2 数字员工管理与服务层：组织岗位、SSO 接入、数字员工、Workspace、WorkItem、知识/记忆服务、Studio、协作、发布和运营。
- L3 业务应用层：销售与售前、岗位协同、教育数字分身等业务 App、行业包和客户配置。

依赖方向为 L3 → L2 → L1。内核使用通用接口与事件，上层消费运行状态和证据。DiAgent 属于内核调度的 Runtime；其推理循环独立于组织服务。

### 2. 数字员工拥有独立的长期身份

DigitalEmployee 由 L2 管理，具有岗位、负责人、职责和服务对象，可以关联多个 AgentDefinition、Deployment 和 Run。Worker 重启、容器替换和 Runtime 变更不改变数字员工身份。

WorkItem 是业务工作，Run 是一次技术执行；一个 WorkItem 可以包含多次 Run。业务完成、复核和验收由 L2/L3 确认。知识、会话和长期记忆由上层服务管理，内核保留执行输入版本、产物引用和访问证据。

### 3. 管理规则转化为可强制执行的约束

L2 解析部门、岗位、对象权限与审批人配置，并下发有可信来源的执行授权。L1 校验调用主体、代表谁执行、资源作用域、有效期、策略版本和撤销状态，在 Run 与工具调用边界执行。

有效权限取调用方、服务、工作负载和资源策略的交集。数字员工 ID、部门 ID 或其他关联标签只用于映射，不能作为权限证明。终端用户通过 L2 获得有作用域的授权，不能借共享管理员身份扩大权限。

L2 负责审批 UI、责任人及升级流程；L1 负责审批门禁。批准必须绑定动作、资源、参数、审批主体和有效期，执行前再次校验；动作或权限变化后按策略重新审批。

知识后端或 L2 在检索与读取时执行源数据 ACL，L1 限制相应工具、凭据、网络与挂载访问。UI 可见性与底层数据访问控制分别验证。

### 4. 保持接口与数据所有权

现有 `/api/os/*` 服务内核管理；`/api/apps/{app}/*` 服务 App；规划 `/api/workforce/*` 服务通用数字员工管理。新命名空间的 Schema、版本和错误契约在 P0 冻结。

同进程调用也需通过受控服务契约，各层独立拥有实体与迁移，上层不直接改写内核表。L1 状态事件与 L2 工作状态通过幂等关联更新，不依赖跨层长事务。

Console、CLI 保留为内核运维入口，并受同一授权机制约束。业务 Portal 使用 L2 服务；同一系统可同时提供这两类入口。

### 5. 模块化起步，面向可扩展企业部署

初期同仓库、同部署；可以共用数据库实例，按模块隔离 Schema 所有权。保持 Migration、接口版本和可替换 Provider 契约。P0 定义容量、SLO 和部署拓扑，P1 保留队列、存储与 Worker 的可扩展契约，P4 验收多节点与高可用；进程和仓库拆分按接口及交付需求推进。

L2 在 P2 建设单企业的部门、岗位、用户与 SSO；L1 在 P1 先提供身份传递、资源授权、凭据隔离和审计能力。多节点与高可用纳入 P4，SaaS 多租户、跨企业计费和多集群治理后置。

Cloud/Local 先统一服务和授权接口；跨节点运行及同步纳入部署拓扑和企业交付验收。

### 6. Registry 与扩展按职责分工

L1 管理扩展身份、版本、摘要、运行入口、依赖、兼容性和执行授权。L2 管理企业目录、审核准入、岗位分配、应用组合与运营。L3 声明业务能力和场景配置。

MCP、Skills、Plugin 包、Connector 和 Runtime 延续 ADR 0002 的独立契约。知识、图谱、记忆与检索通过 Provider 适配。扩展包分发与后端产品部署分别设计。

## 取舍与迁移

三层增加对象映射、授权委托和状态同步成本；统一关联标识、契约测试和幂等事件消费用于控制这些成本。单机模块化部署保持初期运维复杂度可控。

保留现有 Console、CLI、Chat 和 OS API。新增企业服务通过显式映射接入现有 Agent；历史可信操作者入口继续用于内核管理。企业服务开放前，必须完成逐主体与逐对象授权，以及未声明治理配置的受管工作负载准入检查。

共享会话、个人数字分身与记忆建设归 L2/L3；架构说明中原有“多 App 共享会话下沉到 OS”方向由本 ADR 替代。旧路线中 Organization、SSO、Project 和 Environment 全部延期的安排调整为：组织、工作空间、发布环境由上层按阶段建设，内核承接通用作用域。

## 验收

1. 使用上层通用契约完成三类业务闭环，无需在内核增加客户专属分支。
2. 同一数字员工更换 Runtime 或 Deployment 后，身份、任务和工作历史连续。
3. WorkItem 业务状态与 Run 技术状态分别维护，失败、重试和人工复核可追踪。
4. 伪造身份、跨部门越权、过期授权、失效审批和未审批副作用均在相应执行边界被拒绝。
5. 每项成果关联工作、主体、版本、Run、知识/工具来源及审批证据；停用身份后限制新的执行。
6. Console、CLI 和上层 App 通过同一内核策略；新功能同步提供 API 契约与回归。
7. 单节点与多节点安装、升级、回滚和备份恢复覆盖内核、服务对象及产物；扩缩容和节点故障具有任务一致性与恢复证据。
8. 行业包契约支持参考样例以外的新场景，内核不增加客户专属逻辑。

## 路线衔接

P0 冻结契约，P1 建设内核最小受控运行闭环，P2 形成数字员工服务，P3 深化 Studio 和运营治理，P4 交付开放行业包与可扩展部署。三类参考业务验收从 P0 设计，并逐阶段扩大覆盖。
