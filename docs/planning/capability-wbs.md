# DiOS 能力交付 WBS

DiOS 当前开发、部署和工程验收以 Linux（含 WSL）为目标。现有评审业务的 Windows 执行机是外部接入背景，不构成 DiOS Windows 原生支持、安装器、ACL Provider 或后台服务交付要求；新增操作系统支持须有明确需求。

既定目标剩余 **58 项原生能力闭环工作 + 14 项分层任务中的能力工作，共 72 项**。其中实现/集成 27 项、工程验证 35 项、结项评审 10 项。这些是待闭环工作，已有代码与证据列在每项下；工时不同，不据此计算产品完成百分比。

原生 19 张未关闭 Issue 的 101 条原始验收要求全部保留；六张分层任务的 15 条能力验收同时映射。#36 身份部分复用 #33/#35/#38，不重复计数。九张独立应用任务及客户业务模型不计入底座交付。

## 交付顺序与执行规则

遇到技术问题先调研公开发表的研究成果、规范与成熟实现，记录适用前提和代码差距；无适用方案时，先与用户讨论缺口和选择，再设计新机制。

每个 WBS 交付项集中收尾：开发期间只跑受影响测试；交付前集中执行相关回归、构建与部署。已有证据在代码、依赖和运行条件未变化时复用；仅新改动、失败或未解决风险触发重测。用户产品验收单独安排。

**下一项：K01-4.02 协议兼容矩阵收口（#56）。随后推进 K03-2.01 与 K01-4.03 实际控制点资格。** K02-3.02 等待源控制面隔离方式选择，恢复实例保持冻结；选择明确后继续恢复与升级联动。

同一时间只推进一个实现结果。批次按依赖推进，必要的前置资格随首批完成；多节点专属验收统一放在 W4。已通过的证据只在受影响范围复核，原验收通过后停止追加优化。#46 诊断导出按既定后续顺序处理。

| 批次 | 交付内容 | 退出条件 |
| --- | --- | --- |
| W1 | 版本、备份、安装；必要的 Harness/治理资格 | 固定版本完成安装、受控任务、失败回滚和恢复；工程证据完整后进入 G3 接受 |
| W2 | 对象、检索、身份和恢复语义 | 通用对象/Provider 及单节点完整治理契约通过；跨主机条款由 W4 承接 |
| W3 | 包准入、预算、配置、诊断与应用契约 | 包和能力可受控发布、配置、计账、追踪，独立应用兼容通过 |
| W4 | 共享部署、多节点、容量与运营 | 物理跨主机故障、RPO/RTO、两档容量实测及交付接受完成 |

每项完成或阻断时同步状态和证据，每次可部署交付报告完成数、剩余数、下一项与分母变化。连续两小时无可验证结果时披露阻断并复核拆分或切换就绪项。新增范围先说明验收归属与顺序影响；超出既定目标需用户确认。

工程测试、开发部署由 Codex 持续完成；用户参与产品验收。G2/G3 接受按 [工程手册](../engineering/handbook.md) 执行，高影响独立评审人未指定时记待认领。评审项完成不会自动代替其余工作项的工程完成。

基线共 79 项，K02-1.01/.02/.03/.04/.05、K02-3.01 和 K01-4.01 已通过工程验证，共完成 7 项、剩余 72 项；分母未增加。
