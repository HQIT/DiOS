# 修正进程采样后的预试验：并发锁失败与审计缺口

2026-09-30。沿用原两输入、G0/G1/G2、并发1/8/32矩阵、2秒预热/8秒测量窗口及停止阈值，以修正实际服务PID采样后的测量器另存v2重跑。没有调低内存保护线、放宽错误阈值或修改生产逻辑。28项已冻结业务源文件哈希仍一致，11个独立业务对象未用于本轮调试，正式三方比较仍为0。

## 结果与停止原因

原定18格，实际启动9格，均为既有issue开发输入。前8格进入测量，共615次请求，613次成功、2次失败。第9格为G2并发32，预热32次中17次成功、15次失败，触发“基础设施错误率超过5%持续10秒”的停止条件，未进入测量；后9格PR输入未运行。预热失败不能混入615次测量分母，也不能因测量分母为0而将第9格记作无错误。

## 失败请求的执行与证据状态

所有17条失败请求（测量2条、预热15条）对应单元的服务日志均记录SQLite `database is locked`；日志中该异常共17条。G0并发32的失败发生在事件写入；G2的工具失败日志包含调用计数更新锁错误。基础设施500不是策略拒绝，不能计作安全防护成功。

另行只读关联客户端request id、JSON-RPC id、事件/任务、工具操作文件和SQLite审计链，发现4条G2合法请求的`snapshot.read`已在上游执行，但对应`tool_call`审计未落盘：并发8测量阶段1条、并发32预热阶段3条。这4条均未写入报告。其余失败请求没有在工具操作文件中观察到读写；无法恢复事件id的失败明确记为归属未知，不虚构完整事件链。

因此，本轮没有观察到未授权调用，也没有观察到“报告已写入但记录失败”；实际观察到的是**合法读取执行后，调用证据持久化失败**。现有成功请求审计链的哈希有效，不等于失败请求审计完整。原生代理先调用上游、后记录调用决策/提交，后一步失败会留下上述缺口，论文不能无条件宣称所有实际工具执行都具备完整审计轨迹。

这不是仅靠放宽性能阈值能解决的问题，也不能通过删除失败格、盲目重试整个工具调用或只切换WAL后假定解决。存储与外部工具不是同一事务；未来修复必须明确持久化调用意图、执行结果/未知结果、失败恢复与关联语义，避免再次发送工具请求导致重复写入。现阶段只记录问题与修复验收要求，未修改这些工程机制或论文性质声明。

## 性能瓶颈观察

G2单并发的16次工具调用中，HTTP客户端初始化中位数364.49ms，参数授权谓词0.058ms，上游post中位数23.32ms；48次DB提交的单次中位数16.91ms。该结果与v1均显示逐调用客户端初始化成本明显，但绝对数值波动大。尚无连接复用干预，不能把此差异作为已证明的优化收益；这些嵌套跨度与分位数也不能直接相加。

当前SQLite DELETE/FULL、单应用worker及每调用新HTTP客户端是实际测试配置。SQLite锁失败既见于G0，也见于G2，不能简单说它完全由治理判定引入；G2更多持久化与同步初始化可能影响竞争，仍需受控对照。正式测量应把实现成本、授权算法成本与宿主竞争区分开。

## 后续优先级与验收条件

先处理并发持久化和故障审计语义：以本轮保存的失败为回归依据，补充工具未执行、读取已执行、写入已执行但审计失败等有界场景；检查不能出现未授权执行、不能通过重试造成重复写入、无法确认的结果必须可关联地标记未知。缺失的证据不能靠事后伪造为“原子成功”。这些修复只使用开发/受控数据，不使用待复核留出对象调参。

再单列HTTP客户端复用对照，保持任务权限、TLS校验、超时与审计规则一致，保留修复前后结果。之后在稳定隔离环境重跑18格预试验，包含失败格，满足计时/数据/资源验收后才冻结正式5轮长测。当前不直接启动约3.75小时正式矩阵；增加重复时长不能补救已暴露的可用性与证据缺口。

本轮推进的是R1.3/R2.3，同时为R2.2工程假设和审计保证提供了需要响应的新证据。其他环境、非MCP出口、独立复核及正式三方比较仍未完成，不能将此轮视为返修结束。
