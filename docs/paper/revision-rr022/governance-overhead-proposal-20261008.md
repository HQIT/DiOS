# E2AG 治理增量测量方案

2026-10-08。对应 R1.3 与 R2.3 的性能部分。作者已批准按“分阶段计时＋公共路径一致的开关对照＋计时扰动检查”执行。本文档是实验设计，结果另存。

## 已批准的计时与对照细化

在完整路径中以父子跨度记录准入判定、任务持久化、能力签发、调用验证、调用意图、上游往返与响应记录。嵌套跨度扣除子跨度的时间区间并集，不重复相加；剩余墙钟时间包括等待，不称CPU时间。跨请求及父子边界由计时记录验证器检查。

控制配置和完整配置均调用原生MCP代理函数，采用相同上游连接复用、服务查找和响应转发。控制配置在实验进程内替换授权及治理记录函数；路由句柄不产生能力或调用意图记录。两组保留业务事件与任务记录，控制配置不追加治理审计链。原型、生产路由文件与现有服务不修改。重放去重在两组均关闭，以独立到达请求创建新任务；本组测量不包括重复事件处置。

正式测量前，保持完整治理开启，单独比较分阶段计时记录关闭/开启。两工作流各5对、并发1，每配置预热5秒、测量15秒；客户端计时与业务回执在两组保持一致。这个检查衡量分阶段跨度记录的增量，不把“关闭跨度”称为零监测成本。报告逐对变化和波动；若记录扰动足以影响治理增量解释，先调整测量方式并重新核验，不能忽略扰动直接给结论。

部署已核查：测试服务器4个逻辑CPU、约7.25GiB内存，已有其他服务运行。实验应用/执行器/工具共同限制1.5 CPU、1536MiB，独立PostgreSQL限制0.5 CPU、512MiB；使用内部Docker网络，无对外发布端口，不挂载现有业务数据。记录容器CPU节流及内存事件，结论对应这组资源配额，而非整机最大容量。依赖从清华镜像安装到独立目录，不更改现有镜像或服务。资格检查使用确定数量请求，不能用其耗时作为正式性能数据。

## 要回答的问题

在相同业务、代理、工具服务和持久化环境中，启用 E2AG 的授权与证据机制增加多少处理时间，对正常业务完成率和单位时间完成数有何影响？

主要测量对象是 E2AG 整体治理机制的增量，包括授权判定、能力签发、治理状态持久化与证据记录。工具执行时间单列，但治理机制引起的数据库等待和序列化成本仍计入增量。

## 最小对照

| 项目 | 设计 |
|---|---|
| 业务 | 复用两个 VS Code 历史工作流：issue受理摘要（6016字节输入）和PR变更清单（7278098字节快照）；固定正常请求和正确报告，不调用模型API |
| 配置 | G0：同一代理的直通控制配置；G2：完整E2AG，启用准入、能力、调用检查和证据记录 |
| 保持一致 | 来源鉴别、规范化、任务记录、代理路由与连接复用、业务执行器、工具服务、报告验证、后端及耐久性配置、遥测方式 |
| 治理增量 | G2特有的策略、能力、意图与响应审计写入全部保留；G0不伪造这些记录，不删减G2功能以降低开销 |
| 平台 | 优先在DiOS测试服务器的独立测试环境运行，固定资源配额、软件版本和PostgreSQL事务后端；不接生产入口，不使用真实工具凭据 |
| 负载 | 并发客户端数1和8，两种规模；每个客户端一次只执行一个完整业务，完成后发起下一个请求 |
| 重复 | 每个“工作流×并发规模”执行5组G0/G2配对轮次；按预先固定种子平衡运行顺序，单配置预热30秒、测量180秒 |

既有性能驱动的G0直接访问工具，G2经过代理；旧结果因此不是此方案的增量测量。新驱动已补齐同代理的控制配置、服务式后端接入和分阶段计时；测试服务器上的10组小规模验收通过。两配置的正常业务报告正确，资源不匹配请求在G0中执行、在G2中拒绝。正式测量前另行检查跨度记录的扰动。

## 计时与结果

| 指标 | 起止点与解释 |
|---|---|
| 准入路径 | 同一服务进程内，从标准化事件进入调度至关联任务持久化；记录治理判定跨度。需要扣分阶段时明确嵌套关系，不重复加总 |
| 能力签发 | 完整治理配置中，从签发入口至能力持久化且代理配置可用；单列耗时，另计任务可用的整体延迟 |
| 调用前后处理 | 同一代理中分别记录请求进入至上游发送、收到上游响应至返回调用方的跨度；两配置均测。能力检查和调用证据写入包含在内 |
| 工具往返 | 代理发送至收到上游响应，独立记录，用于解释工具等待对端到端测量的影响 |
| 完整业务 | 客户端发起事件至报告写入完成并取得业务回执，报告p50、p95和样本数；离线验证报告内容与记录关联 |
| 负载表现 | 测量窗口内每秒完成的正确业务数、失败数、超时数、截止时在途数；分别报告并发1和8 |

各阶段使用本进程单调时钟；跨进程只按请求标识关联，不相减不同进程的时钟。轻量计时缓存在内存，轮次结束后写出；两配置采用相同计时方式。每条逻辑请求生成独立事件、任务及工具调用标识，报告回执按调用标识关联；事件内容相同，业务对象和规则不随配置改变。

预热任务排空后开始测量，记录排空时长。180秒截止后不再发起请求；窗口内完成数除以180秒得到该负载下的完成速率。截止时在途请求继续等待至预设超时，单列排空期完成与失败，不能并入窗口内吞吐。延迟统计包含测量期发起且最终完成的请求，超时和失败另列，不能通过只保留成功延迟掩盖失败。

比较以配对轮次为单位：报告各轮G0/G2的延迟及完成率，给出每轮延迟差值、相对增量及5轮差值的中位数和范围。请求数不足时标明p95的样本量，不把大量同轮请求当作独立重复。若G0和G2的完成情况不同，先报告成功率差异，再解释成功请求的延迟。

## 执行检查与成本

执行前核对两配置的代理、连接池、工具端点和公共业务路径；确认G2保留全部治理写入，G0直通只存在于隔离实验入口。以正常、拒绝和故障用例检查计时归属与业务回执；这些属于测量工具检查，不扩充安全实验样本。冻结代码、输入、规则、数据库初始化方式、超时和实验顺序，并保存机器与依赖配置。

各轮从独立且同构的业务状态开始。两个配置顺序运行，不同时竞争宿主资源；记录资源占用，基础设施中断单列原因并保留原始轮次。发现实验工具缺陷则停止，修复后整体重测受影响的配对组，不挑选较快轮次。

40次配置运行，每次30秒预热加180秒测量，纯计时窗口合计140分钟；另需环境准备、工具检查、状态初始化与排空时间。具体实现工作量在接口核查后确定。

论文呈现一张分阶段开销表和一张并发1/8的业务延迟、完成率、完成速率表。它们回答治理代价及所测负载下的可用性，不评比外部方法速度，也不搜索最大吞吐或要求并发32全部成功。若仍观察到超时，报告其对增量估计的影响，不转入数据库调优。
