## 已发现问题（暂缓正文修改）

2026-10-01补充核查见[方法闭合审查](contribution-method-audit-20261001.md)。新增必须处理的语义映射：`D_P(e,a)`/逐目标审批与实际事件级聚合不一致；`version`无已实现的决策版本字段，不得混同参数schema版本；能力元组须纳入实际参数约束；调用状态须区分持久意图、结果未知和收到响应；I4的对象依赖验证不能仅引用哈希校验器。复杂度修正可依据现有数据结构直接完成，无需等待性能实验。这些是现有定义的对齐问题，不是层次/能力/治理目标从未定义。

1. **算法辅助过程定义不齐。** `EvaluateContract` 出现在算法中，但算法前主要解释 `EvaluatePolicy`；前者的输入、返回类型及拒绝判定需要对应说明。`ConsumeApproval` 如何把 approved 终态映射为 allow、如何处理 pending/rejected/expired，也需闭合。
2. **大小写和语义映射需要统一。** 数学谓词 `active`、`bind` 与算法过程 `Active`、`BindingsMatch` 的关系没有集中交代；不能仅因名字相似而默认等价。
3. **证据序列起点。** §2.3 写为 l_1...l_n，§4.5 使用 h_(i-1)，代码从 sequence=0 开始、首项 previous_hash 为空字符串。应明确数学索引映射及首项规则。
4. **拒绝路径与审计承诺。** 算法 `AuthorizeCall` 的非活动能力分支直接返回 deny，正文却说两个过程均追加显式阶段结果。后续需核对实现并统一算法与 I4，不能仅以改措辞掩盖缺失证据。

   2026-09-30实现进展：已补齐有效令牌且事件归属可核对的 POST 拒绝调用审计，回归通过，见 `audit-repair-20260930.md`。算法与 I4 尚未改；后续必须明确未鉴别请求、孤立事件、非 POST 和并发/跨事务边界，不能因此取消本项正文对齐任务。
5. **复杂度与实现不一致。** §4.6 假设工具允许集使用哈希集合，实际 `tool_is_allowed` 遍历通配模式；审计追加也要区分逻辑追加与实际列表复制/序列化成本。待最终数据结构和性能实验一起修订。
6. **来源可信性需要明确。** 契约匹配 source/type 不自动等于鉴别真实来源；需解释 Connector 身份验证与标准化字段之间的绑定，再确定 B_C 的前置条件。
