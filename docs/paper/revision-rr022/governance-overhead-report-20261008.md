# E2AG治理增量测量报告

## 结论

40次配置运行全部完成，测量期103389项业务均成功并通过报告内容核验。完整E2AG相对同代理直通配置，单并发的端到端中位延迟增加约28毫秒；并发8时增加约113—115毫秒。相对增量取决于业务：issue受理在并发1/8下分别增加24.34%/77.88%，PR变更清单分别增加6.62%/4.62%。不能将这组结果概括为所有业务均具有低开销。

## 设计及核验

复用两个公开历史开发对象，固定执行器进行快照读取与报告写入，不调用模型。G0/G2均经过原生MCP代理和HTTP连接复用，使用相同业务数据、规则、工具及PostgreSQL。G0只在隔离实验进程内将授权与治理记录替换为直通操作，保留事件/任务记录；G2保留完整授权、能力、意图与响应记录。两组均关闭事件去重，每次到达创建独立任务。详见[批准方案](governance-overhead-proposal-20261008.md)。

两类业务×两个并发数×两个配置×5轮，共40次运行。每次独立数据库，预热30秒、测量180秒；按固定种子变化配对顺序。各轮都通过报告内容、事件—任务—能力—调用关联、实际工具回执及证据链校验；冻结源码在运行前后相同。测量期请求全部完成，失败数为0；截止后排空完成的请求不计入窗口内完成速率。

测试服务器4逻辑CPU、约7.25GiB内存。应用/驱动/工具合计限制1.5 CPU、1536MiB，PostgreSQL限制0.5 CPU、512MiB。Python 3.12.14、PostgreSQL 16.13；后端检查fsync、synchronous_commit及full_page_writes均为on。容器不发布端口，不连接既有业务数据。工具未部署至生产路径。

## 阶段解释

以下为每轮阶段p50的中位数，单位毫秒。工具调用阶段合并每项业务的一次读取和一次写入。阶段采用同进程单调时钟；各阶段分位数不直接相加，嵌套计时不重复加总。

完整治理的issue单并发中，契约、策略、参数检查分别为0.036、0.029、0.040毫秒，能力签发、调用意图与响应记录为4.16、3.83、5.84毫秒。后几项包括状态访问、哈希/序列化与持久化等待，不是CPU耗时，也不能全部归为数据库提交。PR响应记录为11.34毫秒；实现对响应字节计算摘要，大响应会增加这一路径的处理量。

issue并发8的主要增长出现在准入和调用前后处理，工具往返接近。PR并发8的G0/G2均出现CPU配额节流；各5次配置全过程节流计数增量合计约308.90/366.39秒。这是容器计数器，不是测量窗口的纯业务CPU耗时或延迟分解。其业务转换p50也随配置中的竞争情况变化，因此较小的端到端相对差不能解释为治理本身变快。所有组均无OOM终止。

正式运行前的20组计时扰动短测，issue配对p50变化在−0.18%至+0.46%之间，PR在−4.17%至+0.95%之间；本项仅检查并发1。正式比较中两组都开启相同计时，仍按5个配对轮次报告变化范围，不把大量请求当作独立重复。
