> 文章目前的实现主要基于单一Agent OS原型、单一模型、HTTP MCP路径和SQLite后端，建议增加不同Connector、工具传输方式、数据库后端以及其他Agent OS环境下的验证，以增强方法的通用性和外部有效性。

作者答复（供作者确认，未提交）：感谢审稿人的建议。我们按治理接口义务而非平台数量扩展验证：事件接入选择 HTTP Webhook、AMQP 消费和文件投递，分别检验请求鉴别、确认与重投递、完成发布与重复扫描；工具侧比较远程 HTTP 与受控 stdio，状态侧比较 SQLite 与 PostgreSQL。五个单因素主配置各执行八种相同场景，另设两项 AMQP—stdio—PostgreSQL 组合检查，共42项配置—场景运行均符合预期。正常和获批业务合计产生11次预期写入；拒绝或待审批场景不被计作业务完成。重投递未增加任务或产物，撤销后重新初始化与调用均未启动新工具进程。检查器分别读取数据库、实际传输记录及工具产物核验结果。

这些运行使用真实消息代理、数据库与工具传输，接入 DiOS 原生订阅、调度、审批和能力过程；固定执行器替代任务容器，经进程内 ASGI 调用 PEP，不等同于完整生产部署。原有 GitHub、GitLab、Gitea 接入检查仅作为同类入口鉴权证据，不再用平台数量表示机制多样性。跨项目实验另保留11个历史业务对象；42项异构运行不作为独立业务样本。第二种完整 Agent OS 尚未部署，§7.2.3明确将通用性结论限定在所测适配契约和单一宿主内。
