# HTTP 资格与同版本配对准备

2026-10-07。继文件、AMQP、stdio 和 PostgreSQL 资格检查后，补齐真实 HTTP 事件入口，启动[精简方案 v0.3](heterogeneity-protocol-v0.3-20261007.md)规定的同版本配对。本记录只陈述已完成的准备和资格证据，正式配对结果另行核验。

## HTTP 入口

新增 `experiments/e2ag/heterogeneity/http_ingress.py`，在回环网络上实际接收签名 HTTP 请求；管理员配置的固定端点与密钥绑定 `http/fixture` 来源，HMAC-SHA256 校验原始请求体。事件信封复用文件与 AMQP 的 `{id, subject, data}` 格式，并保留统一内容摘要、交付身份和授权相关字段。接收后调用相同的持久交付、原生订阅、准入、审批、能力和调用 PEP，HTTP 返回202表示交付已持久记录，不表示业务必然完成。

这是与另外两个入口对齐的实验适配器，不是修改或替换 DiOS 原有 Git Webhook 路由。三个实验适配器均挂接同一原生治理核心，用于隔离交付机制对授权一致性的影响。客户端至调用 PEP 仍为 ASGI，代理至工具为真实 HTTP 或 stdio；任务容器启动由固定执行器替代，不增加模型调用。

`http-qualification-20261007-v3` 的17项检查及独立 SQL/传输/产物核验通过。其中8项为共同治理场景，3项为接收提交前、提交后及交付完成后的进程中止与响应丢失，1项为相同身份不同内容的显式冲突，5项为错误签名、未配置端点、畸形 JSON、缺字段和保留来源字段。错误输入均在创建任务前拒绝；响应丢失后重投递没有新增任务或工具写入。共观察6次预期工具写入、69个阶段工作进程，不将后者解释为样本量。

首次 HTTP 预检因 Windows 虚拟环境启动器 PID 与实际服务 PID 不同而未找到启动标记，记录于 `http-qualification-20261007-v1`。采用每次启动的唯一标识关联后，v2 的正常/错误签名小试通过。完整 v3 保留运行时源码指纹；运行期间共享工作进程只增加了该组未使用的撤销重连分支，之后检查器增加字段/关联检查。这些变动与正式组重新冻结分开记录，不宣称 v3 与最终正式组使用完全相同的源码。

三入口授权字段、内容摘要一致性与签名体绑定，以及 Windows 实际 junction 拒绝测试通过；与既有文件测试合计17项测试和8个子检查。首次 junction 测试的 PowerShell 参数传递失败、修正后的运行均保留在 `adapter-mapping-regression-20261007-v1.xml` 和 `-v2.xml`。该测试不更改系统目录权限，文件生产者不可并发改写已发布文件仍是部署前提。

## 组合预检与独立检查器

`paired-smoke-20261007-v1` 完成五个主配置的正常业务，以及两个 R5 组合检查，7项行为和独立核验均通过。R5-J01 使用实际代理消息重投递，在消费者终止并恢复后才批准，保留单次审批、任务和写入。R5-J02 先提交撤销并关闭原 stdio 会话，再请求重新初始化和工具调用；两者均被 PEP 拒绝，没有启动新子进程或发送新工具请求。因此这里观察的是重连尝试被授权边界阻断，不是撤销后重新建立了可用工具会话。

独立检查器直接读取 SQLite 或 PostgreSQL 的持久行，核对事件、任务、审批、能力、调用意图与审计链，以及 HTTP/AMQP/stdio 传输记录和工具产物。五项检查器测试包含正确记录、破坏能力关联、错误权限快照、重新计算哈希后删除调用意图，以及额外工具写入；正确记录通过，四种破坏均被发现。结果见 `matrix-checker-regression-20261007-v1.xml`，不把检查器测试计为业务执行。

## 正式配对执行记录

正式组固定 R0—R4 各8项共同场景及 R5 两项组合，共42项配置—场景运行，不增加业务对象。输入、规则、预期、源码指纹在运行前写入 `freeze.json`；任何运行失败都保留原目录，不以新结果覆盖。

`paired-matrix-20261007-v1` 在 R0 的 normal、deny 后，于 pending 启动阶段读取到了尚未写完的 HTTP 就绪标记，未完成该项请求发送。运行停止并保留原记录，隔离数据库与代理容器按自身 ID 清理。启动标记现采用临时文件写完后原子发布，仅改变实验进程同步；治理规则、核心实现、输入和预期未变。`paired-matrix-20261007-v2` 已重新冻结并启动，结果以其完成后独立核验报告为准。

## 六项契约的证据分工

| 契约 | 已有资格证据 | 正式配对的作用 |
|---|---|---|
| 来源绑定 | HTTP 签名/端点拒绝；AMQP 生产消费权限和错误凭据；文件路径、硬链接和实际 junction 拒绝 | 核对各配置规范来源与任务关联；文件 OS 权限由可信管理员配置，不宣称已验证任意身份的文件投递权限 |
| 事件转换 | 三入口字段与摘要对齐；畸形、缺字段和自报来源拒绝；嵌套来源保留为数据 | 核对实际传输输入与落盘规范事件，规则字段保持相同 |
| 事件身份 | 重复扫描/请求/消息；内容冲突显式记录；AMQP 不同身份产生独立任务 | 每场景实际重复交付一次，检查事件、任务、写入数量不增加 |
| 交付与恢复 | 文件6切点；HTTP 响应丢失；AMQP 未确认断连重投递；PostgreSQL 持久恢复 | 主配置核对持久交付与重复处理，R5-J01核对跨机制审批恢复 |
| 强制准入与调用 | 各适配资格的八场景；撤销新会话、审批竞争/终态回归 | R0—R4同版本八场景，R5-J02核对撤销后的重连尝试与新调用 |
| 证据关联 | 两种工具传输的意图/响应故障回归，PostgreSQL 跨会话审计追加，独立证据检查器 | 核对实际行、授权依赖、传输记录与产物；共享核心故障回归复用，不宣称对所有配置重做全部故障组合 |

六项契约用于说明测试义务，不是所有协议的完备分类。文件不可变发布、可信入口配置和单个消费者持有恢复权属于已声明前提；第二完整 Agent OS、任意直接网络/本地进程出口不在本组覆盖范围。该组与原11对象历史业务比较相互补充，不合并样本数，不据此构造外部基线优势。
