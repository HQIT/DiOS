# R1.1 异构机制验证方案 v0.2

2026-10-07。替代 v0.1 的配置范围和执行安排；既有发现、修复及历史结果保留。状态：实验设计，新增 AMQP/文件路径尚未实现或实测。

## 目标与命名

验证更换接入机制、工具传输和存储方式时，E2AG 的来源准入、能力约束、调用门控和授权证据是否保持一致。按协议或接口语义命名实验组，具体软件名称只用于交代可复现实现，不用产品数量替代机制多样性。第二个 Agent OS 完整移植不纳入本次返修，仍不声称跨宿主有效性已得到验证。

接入协议、工具传输和持久化接口是三个不同维度。AMQP 是消息协议，其消息持久化不能代替审批/撤销等治理状态的事务存储；文件既可作为事件载体，也可作为证据落盘方式，这两种用途分开测试。文件系统接口和数据库事务接口不强行称为网络协议。

## 四类事件接入

| 组别 | 协议或交付机制 | 选型理由 | 必查边界 |
|---|---|---|---|
| C1 | HTTP Webhook 请求推送 | 请求驱动、直接接收 | 鉴权失败、重复请求、响应与准入判定分离 |
| C2 | IMAP 邮箱轮询 | 主动拉取、邮箱消息状态 | 邮件标识、同主题不同消息、重复拉取、读取与业务成功分离 |
| C3 | AMQP 0-9-1 消息消费 | 经代理交付、显式确认和重投递 | 未确认断连后的重投递、去重、拒绝事件的确认策略 |
| C4 | 文件投递箱（文件系统接口） | 非网络接口、异步文件交付 | 未写完文件、重复扫描、路径/链接边界、重启后的恢复 |

增加 C3/C4 而不是更多 Git 平台，是因为它们分别引入消息确认和文件交付边界。暂不继续增加 MQTT、Kafka、SFTP 等；若后续确有新的治理性质需要验证，再单独论证。

AMQP 固定版本为 0-9-1，不混用 1.0 的结算语义；二者不是同一协议的简单别名。Broker 实现可选 RabbitMQ，客户端/服务端版本与扩展使用情况在执行冻结时记录。采用 basic.ack/basic.reject 等明确语义，不依赖产品特有扩展得出协议通用结论。

文件入口是受控目录中的事件文件，不是扫描任意工作文件。生产者写入临时文件，关闭后在同一文件系统发布为 ready 文件；消费者只接收完成发布的文件，不通过“等待若干秒”推断写入完成。校验目录归属、符号链接/重解析点、大小、编码、格式和稳定事件标识。跨文件系统移动不纳入原子发布假设。文件名不直接作为授权来源或可执行命令。

## 统一接入契约

适配器从受控连接配置及已验证的交付上下文确定来源，不信任消息内自报的 source、From 或路径。四类输入映射为同一任务目的和资源范围的规范事件，并保留适配前原始标识及映射记录。消息 ID 是去重标识而非身份凭据，按连接器来源命名空间隔离；同一标识但内容不一致的处理须在正式运行前固定，不静默覆盖。

持久记录接收/治理判定后才能确认交付；确认表示系统已接管事件，不表示业务已执行成功。策略拒绝也应留存明确结果后结束该次投递，避免无限重试；暂时性存储失败则保留可重投递状态。格式错误的隔离处理与治理拒绝分别统计。通过稳定标识与持久认领检查重复交付，但不从协议确认或去重单独推导端到端“恰好一次”。

IMAP 的 mailbox 账户鉴权不等于 From 发件人认证；文件入口的来源来自受控投递目录权限；AMQP 的来源绑定队列及受控生产者访问范围，不能只相信消息属性。

## 工具传输与持久化

工具传输保留 MCP Streamable HTTP 与 MCP stdio 两组，使用相同工具定义、参数约束和真实接收记录。stdio 由受控调用代理启动子进程，代理前的 HTTP 链路不变；准确报告变更的是代理到工具这一段。协议握手和工具执行均走真实通道，不以 mock 调用冒充协议支持。

治理状态比较两种部署/存储方式：嵌入式事务存储（SQLite）与客户端—服务端事务存储（PostgreSQL）。统一验收事务提交、条件更新/单次状态转移、持久认领、撤销可见性和恢复，不把 SQL 这一名称当作完整可移植契约。具体类型、驱动及适配差异披露在实现表中。

文件持久化另设有限证据组：将已提交证据追加至文件日志，记录序号、前驱哈希和检查点，关闭/重开后验证完整性，并注入尾部不完整写入进行检测。落盘承诺必须说明 flush/fsync 和文件系统前提；不得以 Python write 返回或存在一个 JSON 文件判定持久成功。源数据库仍保留权威治理状态，文件日志只作为派生证据后端；该组不能写成“全部治理状态已由文件替代数据库”。不为此实现一套自制事务数据库。

## 单因素配置与共同场景

| 配置 | 入口 | 工具端传输 | 权威状态 | 额外证据后端 | 变化维度 |
|---|---|---|---|---|---|
| H0 | HTTP Webhook | MCP HTTP | 嵌入式事务库 | 无 | 参照 |
| H1 | IMAP | MCP HTTP | 嵌入式事务库 | 无 | 接入 |
| H2 | HTTP Webhook | MCP stdio | 嵌入式事务库 | 无 | 工具传输 |
| H3 | HTTP Webhook | MCP HTTP | 服务式事务库 | 无 | 状态存储 |
| H4 | AMQP 0-9-1 | MCP HTTP | 嵌入式事务库 | 无 | 接入 |
| H5 | 文件投递箱 | MCP HTTP | 嵌入式事务库 | 无 | 接入 |
| H6 | HTTP Webhook | MCP HTTP | 嵌入式事务库 | 追加文件日志 | 证据持久化 |

H0—H5 共同验证正常完成、未授权工具、越界资源、审批前、审批后及撤销后调用。分别记录事件、任务/能力、PEP 决策、工具接收、业务产物和审计结果；未创建任务的拒绝分支检查零任务、零调用，不人为跳过准入补发能力。入口特有的鉴权/交付诊断另列，不强行给无网络入口制造网络鉴权用例。

H6 复用 H0 的已提交证据验证落盘、恢复与不完整记录检测，统计口径与权威状态存储分开。所有组保留失败，不预设全部通过；固定工具请求控制模型选择差异，不调用新模型或改动公开仓库。各组不是独立自然业务样本，也不展开全组合。

## 当前基础和下一步

已核查代码仅有 Webhook、IMAP 及内部声明型 Connector；未找到原生 AMQP 或文件消费器。AMQP/文件需要新增有明确配置和调用入口的适配器，进入实际 dispatch_event，不只把合成 CloudEvent 直接塞入测试。IMAP 的标识修复及 4 项新测试、8 项既有回归结果见 [v0.1 记录](heterogeneity-protocol-20261007.md)，不能当作协议链路已通过。

依次完成 IMAP、AMQP、文件接入，再接通 stdio 和服务式事务库，最后执行文件证据组。先完成各组资格检查和必要的最小适配，再冻结用例、源码、依赖和端点版本开展配对。结果稳定后一次性更新正文、R1.1 回复及累计修改稿，不提前把计划写成完成。

旧 11 对象实验的冻结文件和结果不变；新增适配独立记录，影响既有路径时只补相关回归。当前不新增性能调优，不部署到生产邮箱/数据库，不扩成跨 Agent OS 移植。
