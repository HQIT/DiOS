# AMQP 接入资格检查：交付恢复与治理一致性

2026-10-07。对应[精简方案 v0.3](heterogeneity-protocol-v0.3-20261007.md)的 R1 接入资格阶段。19 个场景与3项代理访问控制检查通过，独立证据核验未发现不一致；尚未替代 R0—R5 同版本正式配对。

## 验证问题与实际路径

本组检查将接入从文件投递替换为真实消息代理后，来源绑定、审批和工具授权是否保持，以及未确认消息重新交付是否导致重复任务或工具写入。它检验消息交付与治理状态的衔接，不评价消息吞吐，也不比较方法性能。

实际链路为受限生产者通过 AMQP 0-9-1 发布消息，隔离 RabbitMQ 向消费者交付；适配器校验并规范化消息，持久记录后进入与文件组相同的 DiOS 原生订阅、准入、任务创建、审批、能力签发和调用 PEP。固定执行器通过 ASGI 调用原生 PEP，代理再通过真实 HTTP 访问工具。工具独立记录收到的请求及写入产物，不设置第二道权限过滤来掩盖 PEP 漏放。

RabbitMQ 实测版本3.13.7，Pika 1.3.2；代理与管理接口只绑定回环地址。Broker 镜像 ID 为 `sha256:1031d41f3f1611f61f0fe9011e26201967f460f93f96f92d5be0e823d59e7541`。使用临时随机凭据及独立虚拟主机，未使用生产服务或外部仓库。任务容器启动仍由确定性执行器替代，工具请求不由模型生成；这是机制适配验证，不是完整 DiAgent 部署实验。

## 接入和交付契约

消费者只能读取受控队列，不能发布或配置资源；生产者只能向指定交换机发布，不能读取或配置资源。事件来源固定为配置对应的 `amqp/fixture`，不从载荷自报字段推导身份。该设置建立受控队列和生产者权限边界，不证明任意生产者提交的业务内容都可信。

消息体必须具有 id、subject 和 data 三个字段，AMQP message_id 必须与消息体 id 一致。应用事件身份是“受控来源＋事件 ID”，不是通道内的 delivery_tag。同标识同内容重复交付返回原事件关联；同标识不同内容写入冲突记录；同内容不同标识仍作为两个事件处理。交付确认只表示交接状态已经持久化，不代表业务获准或完成。

采用手动确认，并在持久交接之后确认消息。进程中止测试等待旧进程明确退出后才恢复消费者；消息代理的 redelivered 标志、队列状态、应用数据库以及实际工具写入共同核对。发布者确认和消费者确认分别观察，二者并不等价。这一处理与 RabbitMQ 3.13 的[确认与重投递语义](https://www.rabbitmq.com/docs/3.13/confirms)一致；资源权限配置依据其[访问控制文档](https://www.rabbitmq.com/docs/3.13/access-control)。

## 结果

| 检查组 | 场景数 | 实际观察 |
|---|---:|---|
| G01—G08 共同治理场景 | 8 | 正常任务和审批后任务完成；来源拒绝、待审批不调用工具；未授权工具、越界资源、撤销及过期能力请求均被调用 PEP 拒绝 |
| 接收提交前、接收提交后、交接提交后进程中止 | 3 | 均收到代理真实重投递；恢复后各仅一次正常工具写入 |
| 待审批消息交接后中止，恢复后保持待审批或再批准 | 2 | 重投递不绕过审批；批准场景只完成一次有效审批转换和一次工具写入 |
| 同标识不同内容、同内容不同标识、数据内自报来源 | 3 | 冲突持久记录；新标识产生独立任务；数据内 source 不覆盖受控来源 |
| 畸形 JSON、额外顶层 source、message_id 不一致 | 3 | 均拒绝进入准入；零事件、零任务、零工具请求，消息保持未确认 |
| 错误密码、读取其他队列、向其他交换机发布 | 另3项 | 认证或代理权限检查拒绝；后两项返回 AMQP 403 ACCESS_REFUSED |

四项工具边界拒绝分别记录 `MCP_TOOL_NOT_GRANTED`、`MCP_ARGUMENT_ENUM_DENIED`、`TOOL_GRANT_NOT_ACTIVE` 和 `TOOL_GRANT_EXPIRED`，不是仅凭 HTTP 403 推断拒绝原因。过期场景将已签发能力有效期设为过去时间；撤销场景在撤销提交后发起新调用，均不涉及撤回已经执行的操作。

19 项场景满足各自预期，实际10次工具写入与业务产物逐项一致。运行器之外的检查程序直接读取磁盘 SQLite、审计链、工具接收文件、工作进程输出和代理队列观察记录，核验计数、对象绑定、哈希顺序、审批状态及重投递，结果为通过。独立指检查实现与执行器分离，不是外部人工复核。87 次工作进程用于阶段隔离，不计作87个独立样本。

## 初次失败与运行修正

首轮 v1 的代理访问控制检查通过，但首个业务消费者在连接时失败，随后已有连接收到代理 shutdown 通知。未取得完整业务结果；代理自动删除还使清理命令返回“容器不存在”。该轮源文件指纹、访问控制结果、逐项错误与原始进程输出均保留，不计入有效业务实验。

第二轮仅调整实验容器生命周期：保持一个前台 WSL 会话，保留容器至收集状态和日志后再清理。没有修改治理规则或放宽场景预期。重跑结束时代理仍运行、未发生 OOM，19项场景和独立核验通过。第一轮 shutdown 的底层触发原因没有充分日志确认，不将 WSL 空闲退出写成已证实根因。

第二轮运行前冻结69个 Python 源文件，运行后指纹变化数为0。提取文件/AMQP 共用的消息规范化函数后，文件入口及准入的22项回归检查通过、无跳过，单独保存为文件资格 v2。此次没有修改后端核心文件。

执行代码为 `experiments/e2ag/heterogeneity/amqp_ingress.py`、`run_amqp_qualification.py` 和共用工作进程 `run_file_recovery.py`；核验代码为 `check_amqp_qualification.py`。

本组支持所测 AMQP 配置与治理核心的衔接有效；它不证明所有 AMQP 实现或任意交付交错。未测试代理重启、网络分区、TLS 和多个消费者同时争用同一来源。畸形消息保留未确认，并保存原始输入及拒绝输出，尚未实现生产环境隔离队列处置。文件组已经观察到的任务中途未决边界仍保留，不能由本组几个成功恢复切点推导普遍的恰好一次执行。
