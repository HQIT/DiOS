# 文件接入：持久交付、进程恢复与真实工具资格检查

2026-10-07。对应[精简方案 v0.3](heterogeneity-protocol-v0.3-20261007.md)的文件入口资格阶段，不是六配置正式比较，也不是新模型实验。

## 实际执行路径

读取真实 ready 文件，经适配器的持久交付记录进入 DiOS 原生订阅匹配、dispatch_event、a2a_service.send_message、任务创建、能力签发和调用 PEP，再以真实 HTTP 连接访问本机隔离工具端。工具端将收到的请求和实际写入产物分别落盘，允许所有收到的工具请求，避免用上游拒绝掩盖 PEP 漏放。

替换点只有任务容器启动函数：用确定性执行器代替 DiAgent 容器与模型，读取事件中的 text 并产生大写报告。调用 PEP 通过 FastAPI/ASGI 入口执行；代理到工具走真实 socket，客户端到代理不走外部 TCP。这些替换不是策略判定替身，不把此实验称作完整 DiAgent 部署。执行器、代理、数据和工具实现需在正式配对中保持一致。

状态保存在独立磁盘 SQLite。每次接收、重复交付、审批和快照检查在新 Python 进程中运行；恢复前等待旧进程返回明确终止码，不能因观察超时就接管仍存活的消费者。69 个工作进程用于15个场景的阶段隔离，不是69个独立业务样本。

## 交付适配与边界

新增交付记录表按“受控来源＋投递 ID”唯一认领，保存内容摘要以及 received/dispatching/recorded 阶段。相同标识同内容返回原事件关联；内容冲突单独落盘，不覆盖原事件或新建任务。交付记录的保留期独立于原分发器的一小时去重窗口，本轮未实现清理策略。

received 记录提交后再进入准入，准入交接已落盘后才返回可确认信号；拒绝与待审批同样形成可恢复记录。交付确认不表示业务执行成功。适配器尚未安装为后台消费者，文件本身保持在测试目录，确认状态由持久记录表表示；不得描述为已验证生产目录归档/删除机制。

单一配置消费者、可信配置与发布后不可改写文件是当前前提。恢复只在确认原消费者退出后启用。若原生事件处于中间状态、无法确定任务是否完整执行，保留 unresolved、不确认、不自动重新启动任务；不能将这种安全停止称为自动恢复完成。

## 结果与修复前后

| 检查类别 | 观察结果 |
|---|---|
| 正常任务、审批后任务 | 各产生一次正确工具写入；后续重复交付不增加任务或写入 |
| 来源拒绝、待审批 | 无工具调用；待审批记录跨进程保留 |
| 未授权工具、越界资源、撤销后、过期后调用 | 均返回调用 PEP 拒绝，工具端零对应请求 |
| 同标识不同内容 | 内容冲突持久记录，原事件/任务保留，无第二次工具写入 |
| 接收提交前、接收提交后、分发前中止 | 新进程继续处理，最终每个场景仅一次正常写入 |
| 分发提交后、交接记录提交后中止 | 新进程识别已处理状态，不重复执行 |
| 任务创建后、容器启动替换点中止 | 保留一个未完成任务，不确认交付、不重新启动，零工具写入；需进一步核对执行状态 |

能力过期场景将已签发能力的有效期设置为过去时间，核对真实验证路径；不称为长时间自然等待实验。撤销通过原生 revoke_task_grants 后发起新调用，不涉及撤销已经执行的外部操作。

第一次 v1 运行的15个行为场景满足预期，但单独编写的证据检查器直接读取磁盘数据库、工具接收记录及产物后，发现4个调用拒绝场景缺少任务审计关联。定位为 event_dispatcher 只给非 failed 返回任务追加 a2a_task 记录；审批恢复路径也有同样遗漏。新写的2项针对性测试在修复前均失败，补齐这两个分支后通过。没有改变任何授权允许/拒绝条件。

修复后以新目录重跑同样15个场景，15项行为检查及独立证据检查通过。全组实际8次工具写入与预期内容一致，6个故障切点中的5个完成恢复、1个保持显式未决。这里“15项通过”包含正确识别未决状态，不等于15项业务都成功，也不证明覆盖全部崩溃交错。

随后执行后端全部 `test_e2ag*.py`，101 项测试通过（包含上述2项新回归）；`git diff --check` 通过。运行结束核对 v2 启动前冻结的源码清单，指纹不匹配数为0。测试耗时不作为方法性能证据。
