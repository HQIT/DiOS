# 架构原则

版本：0.3 · 状态：已接受（G0） · 适用范围：L1 内核、L2 管理与服务、L3 应用及扩展。

## 设计起点

企业数字员工需要长期身份、可管理的能力、明确授权、可恢复的执行和可验收的成果。业务变化快于运行基础设施；组织规则、行业规则与运行机制具有不同的变化周期。以此划分职责，可以在增加业务应用、更换 Runtime 或扩展部署时保留稳定核心。

“OS”定位体现为统一管理执行资源、生命周期、调度、隔离、授权和运行证据。管理服务通过受控契约使用这些能力，行业应用以服务契约组合业务流程。

## 原则与约束

| 编号 | 原则与依据 | 工程约束 | 验证方式 |
| --- | --- | --- | --- |
| AP-01 | **按责任与变化原因分层。** 运行机制、组织管理、行业流程各有生命周期。 | L3 → L2 → L1；L1 只识别通用运行对象与授权声明。层间经公共契约通信；每层拥有自己的数据模型和迁移。 | 依赖审查；禁止跨层直接读写表；契约测试。 |
| AP-02 | **长期身份独立于执行实例。** 数字员工和工作记录需跨版本、重启与 Runtime 存续。 | DigitalEmployee、WorkItem 属于 L2；Revision、Deployment、Run、Attempt 属于 L1。逻辑运行的重试保留 Run 标识并创建新 Attempt；分工或业务修订可创建新 Run。映射采用稳定标识，引用固定版本。 | 更换 Runtime 和重新部署后，身份、工作历史与产物关系可追溯。 |
| AP-03 | **技术完成与业务验收分别建模。** 执行成功不自动满足业务质量要求。 | Run 通过完整性与已登记结果校验后记录技术成功；L3 提供领域证据规则与校验器，L2 组织业务复核。WorkItem 记录分派、协作、复核与关闭。 | Run 成功但成果被退回、多个 Run 合成一项成果、人工接管等场景。 |
| AP-04 | **在实际访问边界授权。** 请求、配置和模型输出均可能携带未经授权的动作。 | L2 解释组织权限；L1 校验主体、代理链、资源范围、策略版本和有效期。知识读取执行源数据 ACL；默认拒绝未授予能力。 | 越权、过期、撤销、参数变化、审批重放和跨对象读取回归。 |
| AP-05 | **可恢复执行与可追溯副作用。** 网络重试、Worker 故障和外部系统超时是正常运行条件。 | 持久状态、租约及 fencing、幂等键、重试预算、取消与补偿有明确语义；Run、Attempt、Worker 进程、Agent Session 分别标识。观测超时进入待确认；未知外部结果先对账。 | 重复投递、Worker 重启、租约过期、响应丢失与恢复演练。 |
| AP-06 | **发布可重现，变更可回退。** 相同配置需能定位实际执行版本。 | Revision 固定代码、依赖与配置摘要；Deployment 指向已验证版本。数据库迁移有兼容期和恢复方案，回滚应用与恢复数据分别设计。 | 固定版本重放、升级兼容、回滚和干净环境恢复。 |
| AP-07 | **通过契约扩展与替换。** Runtime、模型和知识后端将持续变化。 | Adapter 与 Provider 声明能力、版本、失败语义和健康状态。MCP、Skills、Connector、A2A、Plugin 各有职责；插件分发与后端部署分别治理。 | 替换 Provider/Runtime 契约回归；扩展包兼容、来源与许可检查。 |
| AP-08 | **从模块边界演进部署。** 初期控制复杂度，同时支持企业规模。 | 先模块化实现；持久任务与 Worker 解耦。可扩展部署的会话、任务、产物和授权状态进入共享持久服务；高可用按故障域设计。 | 多进程/多节点运行、节点丢失、滚动升级、容量与恢复验收。 |
| AP-09 | **运行证据与业务结果关联。** 企业需要解释谁以什么权限执行了什么。 | 贯通 WorkItem、Run、Attempt、Worker/Process、Session、Trace、Revision、策略、审批与产物标识；审计脱敏、访问受控、保留期可配置。 | 从成果回溯主体、输入版本、工具动作和授权决议；敏感信息泄漏检查。 |
| AP-10 | **接口和文档随行为变更。** UI、CLI 与服务调用需要同一语义。 | 公共 Schema、错误、状态和权限统一；变更同时覆盖 API、CLI、Console/门户、文档与契约测试。 | 消费方兼容矩阵和代表性端到端验收。 |
| AP-11 | **质量目标驱动技术选择。** 容量、成本与可用性需要可测量依据。 | 先定义工作负载、时延、并发、恢复和成本指标，再确定数据库、队列、部署规格与伸缩阈值。 | 负载报告、SLO 仪表、故障演练、成本样本；实测值与目标值分别记录。 |
| AP-12 | **智能体实现中立，loop/harness 可替换。** 数字员工需要使用不同来源的 Agent。 | 通过 A2A、ACP（Agent Client Protocol）及厂商适配接入；协议交互与进程生命周期分别建模，能力、版本与治理控制点显式声明。 | 不同来源 Agent、会话/任务映射与实际权限约束验收，见 [开放智能体接入](agent-interoperability.md)。 |
| AP-13 | **E2AG 随接入能力持续演进。** 代理权限必须在执行链路落实，控制范围随工具与 Harness 变化。 | L1 统一策略决策、执行控制点和证据契约；MCP 网关、原生工具沙箱与可信钩子按路径接入。受管工作负载按已验证治理能力准入；缺口形成扩展任务、回归与性能验收。 | 第三方 Agent → E2AG → 实际工具的拒绝/审批/撤销/未知结果验收；续期、委派、性能与兼容回归，见 [ADR 0005](../adr/0005-e2ag-integration-evolution.md)。 |

## 重点取舍

AP-04 的授权强制执行范围以实际控制点为准：远端委派型 Agent 按端点准入、数据外发与任务边界治理；逐工具审批需远端提供可验证控制能力。AP-06 的版本重现对托管执行固定构建，对外部端点保存声明版本与能力快照，并标记不透明部分。

初期采用同仓库的模块化结构，可在同一进程运行；跨模块仍保留显式接口和所有权。服务拆分由容量、故障隔离、发布频率或安全边界驱动，并记录收益与运维成本。

跨系统副作用采用可重试与对账机制。平台的幂等键只能约束支持相应语义的执行边界；外部系统是否支持去重、查询执行结果和补偿，需要逐个 Connector 说明。

高风险动作优先保证授权与证据完整性。策略、审批或必要审计写入不可用时，受影响动作停止并形成明确错误。只读低风险能力如需降级，必须在策略中显式定义范围、时效和证据补记方式。

目标支持单企业内多部门、多用户、多岗位与多节点部署。多租户作为独立架构决策后续评估；对象归属、授权范围和可迁移标识在当前设计中保持明确。专业服务、岗位协作与数字分身用于检验通用性，应用范围持续开放。

## 原则变更

原则编号保持稳定。新增或修改原则时关联需求、受影响契约、替代方案与迁移计划，通过 ADR 记录决议；工程手册规定评审与基线更新方式。例外须有责任人、范围、到期条件和验证证据。
