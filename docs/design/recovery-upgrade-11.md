# 升级失败后的干净恢复

固定候选版本启动失败后，DiOS 从备份恢复到新目录，保持两层执行冻结；原结果经新证书和当前 E2AG 对账后，由管理员确认源端隔离并启用，再以原稳定版本恢复服务。候选版本随后可重新升级，任务、尝试、会话和产物保持原关联。

## 部署与恢复顺序

1. 固定原版本、候选版本和故障候选的镜像摘要；备份数据库、配置、workspace 与相关产物。
2. 已启动任务保留原执行。候选启动失败后停止源服务，确认原执行已退出；恢复到新目录。
3. 恢复实例提供只读观察并保持 `restore_hold`。旧证书和被撤销的当前授权拒绝访问；原结果通过重新认证补回。
4. 对账完成后停止恢复实例，执行 `installation-activate`；两库原子解除冻结。以原稳定版本启动服务，处理原排队任务。
5. 重新升级候选版本，通过 API 核对任务身份、尝试及产物。

隔离、对账和离线启用要求见[恢复启用](installation-activation-11.md)，原理依据见[恢复研究](recovery-research-11.md)。未知外部副作用保持人工对账要求。

## 固定版本与实测

原版本源码为 `33e898ba9bfe761cbe8fad29a45b3f61f1cc6c66`，候选为 `5ed239caf992165ffe928c0c4d14bf2235ff9381`。两镜像分别有 249、251 个应用文件与源码逐文件匹配；完整镜像摘要、源码摘要及任务证据见[验证报告](evidence/recovery-upgrade-20261127.json)。故障候选在启动时明确退出，退出码为 1。

RTO 从停止原 API、开始启动故障候选计时，到恢复后原排队任务完成且通过 API 可见，实测 **31.627 秒**。只读 API 可用时间另列，避免以健康检查代替恢复执行能力。

这是一台 Linux/WSL、SQLite、两个合成任务和兼容 Schema 的单次功能演练。镜像已在本地，管理员确认由隔离夹具提交；镜像下载及人工排障等待时间另计。企业负载、共享后端及多节点 RTO/RPO 分别沿 D01-2.03、D01-3.03、D01-4.01 验证；Schema 变更升级由相应迁移兼容门槛约束。
