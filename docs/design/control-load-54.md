# 控制面 HTTP 容量基线

本基线测量 DiOS 的任务受理、列表、详情、对象隔离、幂等重放与 E2AG Work 撤权。测试使用正式 Runtime HTTP 路由、访问令牌中间件和持久数据库；不启动 Worker 或模型任务。工作项为 D01-4.01。

## 负载与口径

采用 [k6 1.4.0](https://github.com/grafana/k6/releases/tag/v1.4.0)，镜像固定摘要。并发矩阵为 1/8/32/128 个 HTTP 客户端，每组 256 个混合操作；到达率矩阵为每秒 10/100 个混合操作，持续 10 秒，每组最多 128 个客户端。两类矩阵各重复三次，每组使用新建隔离数据库和两个不同主体的种子任务。

混合操作中 70% 为列表/热点详情查询，20% 为读取另一主体任务并预期拒绝，10% 为受理、相同键重放和撤权三步流程。到达率是混合操作数，写流程包含三次 HTTP 请求，实际 HTTP QPS 单列。普通查询流量不能直接等同于容量设计中的纯查询 QPS。

[k6 的开放与封闭负载模型](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)区分固定并发与固定到达率。固定到达率不随响应变慢降低目标负载；未能启动的操作计入 `dropped_iterations`。本基线同时记录计划操作数、实际完成数、成功率、丢弃、各操作 P95/P99、写入队列超时与服务器 CPU 时间。

持久配置从实际数据库读取 `journal_mode` 与 `synchronous`，不以设计文档代替。现有新建 Runtime 数据库使用 SQLite DELETE journal、FULL 同步；负载脚本不修改后端参数。CPU、内核、依赖、镜像与源码摘要随报告保存。压测端与服务端同宿主，内存指标为 Python 进程运行期间的峰值。

## 一致性判定

每个成功受理必须有 Work 授权；同键重放返回原 Run；撤权成功返回 `revoked`；另一主体不能读取任务；所有任务均没有 Attempt。结束后核对数据库任务数、撤权数与已完成写流程数。

高负载下受理成功、撤权超时会留下部分流程，报告中的 `accounting_consistent=false` 表示完整流程数与最终状态不相等，需要检查各阶段失败。该字段不单独判定数据库损坏。失败请求、部分流程与丢弃操作均保留；不通过自动重试隐藏过载。

`passed` 只表示本组短时负载全部完成且断言通过，未包含两档 SLO 的接受判定。HTTP 客户端数量与 Agent 实际执行并发分别计量；本基线没有实际 Agent 执行并发。

固定到达率在停止边界可能多启动一次操作，见 [k6 #3052](https://github.com/grafana/k6/issues/3052)。判定保留实际数量，允许目标数或目标数加一；少完成、丢弃、请求失败和部分写流程均不通过。固定迭代数模式要求数量完全相等。

## 运行

```bash
docker pull grafana/k6@sha256:6a3ee54ac0e9ff5527923f6295257453dd88012f32f40dadf0eb1b638cbb21c7
backend/.venv/bin/python scripts/qualify_control_load.py \
  --output workspace/control-load-new
```

测试只绑定本机回环地址，每组独立临时库与身份目录，使用随机容器名。结束时关闭对应服务、回收本次 k6 容器并删除临时令牌。原始 k6 日志、分组统计和总报告保留在指定目录；发布报告不含身份凭据。

## 剩余资格

TLS、完整工具允许/拒绝/审批混合、长委派链、实际 Worker、90 天历史数据、预热及持续负载、跨主机、复制恢复与单位成本仍按 D01-4.01 原要求验收。物理限制相关实测按用户安排暂缓，原待验项及分母保持不变。

## 本次结果

18 组测试采用上述矩阵与三次重复；9 组完整完成，9 组出现请求失败、丢弃或部分写流程。所有组的语义错误计数为零，未启动任何 Attempt。原始测量值和判定依据见[完整证据](evidence/control-load-20261128.json)。

| 负载 | 完整完成组数 | HTTP P99 范围 | 写队列超时总数 | 丢弃操作总数 |
| --- | ---: | ---: | ---: | ---: |
| 1 并发 | 3/3 | 0.37–0.40 秒 | 0 | 0 |
| 8 并发 | 3/3 | 2.49–2.73 秒 | 0 | 0 |
| 32 并发 | 0/3 | 9.83–10.54 秒 | 35 | 0 |
| 128 并发 | 0/3 | 14.74–15.00 秒 | 48 | 0 |
| 10 操作/秒 | 3/3 | 0.50–7.18 秒 | 0 | 0 |
| 100 操作/秒 | 0/3 | 14.60–15.00 秒 | 41 | 2277 |

8 并发下请求均完成，整体 P99 已达约 2.5–2.7 秒；32/128 并发出现写队列超时。10 操作/秒的三次运行均无请求失败或丢弃，但一次 P99 达约 7.2 秒，当前短时结果不足以确认稳定容量。100 操作/秒下出现明显丢弃及超时。

下一步在 D01-4.01 内定位查询事务开销、SQLite 读写竞争与有界背压，先按 SQLite/SQLAlchemy 的公开方案验证最小调整，再复测受影响档位。保持 FULL 持久保证、E2AG 授权与必要审计；不延长超时来掩盖积压，不启动新一轮存储选型。
