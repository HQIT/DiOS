# 审批资格变化与执行复核

所属：#35 / K03-3。审批人的组织角色、岗位和业务范围由上层应用或身份 Provider 管理；DiOS 在批准和派发控制点验证审批资格，保存绑定、决定及失效证据。

## 成熟机制与职责

[OPA 的策略解耦](https://www.openpolicyagent.org/docs/philosophy)将策略判定与执行控制分开。沿用现有 OPA Data API、版本化工具注册和 Runtime 事务审批账本：OPA 检查工具权限及参数，Runtime 验证具体 Run/Attempt/Session、审批资格和单次消费。此次补齐等待后的复核与既定 `approved → invalidated` 状态转换，不增加授权后端。

[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)提供 subject/actor 和委派表达；三层委派的权限交集、期限收窄和上游失效传播继续按[授权契约](authorization-contract-v1.md)实施。本页验证审批资格变化，不计作委派链验收。

## 执行规则

批准时，在 OPA 查询及工作绑定复核结束后，重新认证审批凭据并检查调用者对象权限。派发时，在预检、MCP 初始化后的提交检查和 OPA 返回后的检查中复核原审批人资格。

确定原审批人已失去资格时，在当前 Runtime 事务中将调用设为 `denied`、审批设为 `invalidated`，增加版本并记录失效原因。保留原审批人、审批说明、参数和执行绑定。恢复账号不恢复旧审批；新请求使用新调用身份并重新审批。无关审批人的变化不影响当前合法审批。

Provider 不可用、配置格式错误和 OPA 超时阻断本次派发，保留审批供恢复后重新检查。已派发调用继续保留原始回执与未知结果对账规则；历史回执恢复不签发新执行权限。

API 返回 `TOOL_APPROVAL_INVALIDATED` 说明旧审批已终止；Worker 自动工具通道读取同一账本。Console 显示中英文失效标签和重新申请提示，不显示批准或派发入口。既有字符串状态列能够保存失效状态，本次无数据库结构迁移。

## 验证

[验证证据](evidence/approval-qualification-20261124.json)记录：

- 修复前，真实 OPA 等待期间撤权的两个交错场景均未阻断批准或派发；修复后通过。
- 真实 OPA 与 MCP HTTP 8 项通过，覆盖批准等待、最终派发等待、原审批不可复活、新审批可执行，以及既有策略变化和故障场景。
- 工具专项 15 项通过，包含 MCP 初始化期间范围撤回、无关身份变更和 Provider 故障恢复；全量后端 552 项中 421 通过、131 条件跳过。
- 开发浏览器发起真实任务，原生 Worker 等待审批；暂停该测试容器后批准并撤回审批资格，恢复进程后确认调用被拒且无派发意图。恢复审批人后原申请仍无法重新批准；原 Attempt/Session 退出，中英文及移动界面 6 项检查通过。

开发验证保留原 77 条记录，新增 1 条资格任务，当前 78 条、无活跃任务。审批人配置已恢复。浏览器脚本 `scripts/probe_approval_invalidation.mjs <private-fixture> <output> [run-id]` 在省略 Run ID 时发起一条本地开发任务；传入 Run ID 时只检查该历史记录。fixture 结构沿用[标准注销验证](backchannel-logout-35.md)，秘密不进入版本库。

## 剩余保证

当前文件 Provider 的配置更新与 Runtime 数据库提交属于两个独立写入路径。复核覆盖已观测撤销及上述等待窗口；跨 Provider 严格撤销排序仍需单独协调与验收。一次未被任何控制点观测到的撤销再恢复，不能靠当前文件快照重建历史。后续按成熟授权服务的版本/一致性机制推进，保持 #35 开放。
